### Task 1: Bug A — Mis Tareas filter-chip layout

**Files:**
- Modify: `app/(tabs)/tareas/index.tsx:135-151` (JSX), `app/(tabs)/tareas/index.tsx:229-234` (styles)

**Interfaces:** None — pure style/JSX change, no new exports, no consumers.

**Root cause:** The horizontal filter-chip `ScrollView` has no `style` prop, only `contentContainerStyle`. Without an explicit `style` bounding it, React Native's Yoga layout can give the `ScrollView` an unstable height on Android (a well-documented `flexGrow`-related quirk for unstyled horizontal `ScrollView`s), and the content container's default `alignItems: "stretch"` then stretches every chip `TouchableOpacity` to match whatever height Yoga computed — producing "elongated" pills, or pills tall enough that the text visually sinks toward the bottom. This has nothing to do with the actual number of tasks (`FILTER_CHIPS` is a fixed 5-item array); the reported task-count correlation is because the height Yoga computes depends on how much space the sibling list/empty-state below happens to claim during that layout pass.

- [ ] **Step 1: Give the ScrollView an explicit non-stretching style and fix the row's cross-axis alignment**

In `app/(tabs)/tareas/index.tsx`, change:

```tsx
      <ScrollView
        horizontal
        showsHorizontalScrollIndicator={false}
        contentContainerStyle={styles.chipsRow}
      >
```

to:

```tsx
      <ScrollView
        horizontal
        showsHorizontalScrollIndicator={false}
        style={styles.chipsScroll}
        contentContainerStyle={styles.chipsRow}
      >
```

- [ ] **Step 2: Update the styles**

Change:

```tsx
  chipsRow: {
    flexDirection: "row",
    gap: 8,
    paddingHorizontal: 20,
    paddingBottom: 12,
  },
```

to:

```tsx
  chipsScroll: { flexGrow: 0, flexShrink: 0 },
  chipsRow: {
    flexDirection: "row",
    alignItems: "center",
    gap: 8,
    paddingHorizontal: 20,
    paddingVertical: 12,
  },
```

`flexGrow: 0` / `flexShrink: 0` on the `ScrollView` itself stops it from being stretched by its flex-column parent. `alignItems: "center"` on the row replaces the default `"stretch"`, so every chip sizes to its own natural content height instead of stretching to match a miscomputed row height — this is what actually fixes both symptoms (elongated pills, text stuck to the bottom).

- [ ] **Step 3: Manual verification (no automated test — pure layout fix, matches this codebase's convention of no `.tsx` component tests)**

Run:
```
npx tsc --noEmit && npx eslint app/\(tabs\)/tareas/index.tsx && npx prettier --check app/\(tabs\)/tareas/index.tsx
```
Expected: all clean. Note in the PR/commit description that visual confirmation at 0, ~4, and ~20 tasks happens on the human's on-device checklist (Task 7 below), since this is exactly the layout quirk that doesn't reproduce reliably in a non-device renderer.

### Task 3: Bug C — bottom safe-area padding on non-tab screens

### Task 4: Bug D — heads-up reminder notifications via a new channel

**Files:**
- Modify: `src/lib/notifications/index.ts:3` (constant), `src/lib/notifications/index.ts:25-30` (`ensureReminderChannel`)

**Interfaces:**
- Consumes: `Notifications.setNotificationChannelAsync`, `Notifications.AndroidImportance` from `expo-notifications` (unchanged).
- Produces: `REMINDER_CHANNEL_ID` (private, used internally by `scheduleReminderNotification`'s `channelId` and by `ensureReminderChannel`) — value changes from `"reminders"` to `"reminders-v2"`. No exported signatures change.

**Why a new channel id:** confirmed against the SDK 57 docs (`https://docs.expo.dev/versions/v57.0.0/sdk/notifications/`) — once a channel is created on-device, only its `name`/description can be changed later; `importance` cannot be raised on an existing channel (Android OS limitation, not an Expo limitation). Any user who already has the app installed has a `"reminders"` channel stuck at `DEFAULT` importance forever. A new channel id is the only way to get heads-up (banner) behavior for existing installs too.

**Why `sound: null`:** the SDK 57 `NotificationChannelInput` type has a `sound: string | null` field. Per this task's explicit constraint ("Sonido por ahora NO — decisión pendiente"), the channel must NOT play a sound; leaving `sound` unset would fall back to the Android default channel sound, so it must be passed explicitly as `null`.


to:
```typescript

```

- [ ] **Step 2: Raise importance to HIGH and explicitly silence the channel**

### Task 6: Feature F — onboarding asks for a nickname after creating the semester

**Files:**
- Create: `app/onboarding/perfil.tsx`
- Modify: `app/onboarding/primer-semestre.tsx`, `app/_layout.tsx`

**Interfaces:**
- Consumes: `saveProfile(profile: Profile, database?: Database): Promise<void>` from `src/db/repositories/settings.ts` (existing, tested — `Profile = { nickname: string | null; fullName: string | null }`).

**Why this needs a root-layout change, not just a new screen:** `app/_layout.tsx` owns ALL onboarding→tabs navigation via a `useEffect` that watches `activeSemesters` (a live DB query) — this exists specifically to avoid a race that was already hit and fixed once before (see the large comment block above that effect): navigating forward from inside an onboarding screen, before the layout's own live query has caught up, causes the layout to bounce the user back. The layout's redirect-to-tabs condition needs a narrow, explicit exception for the new `/onboarding/perfil` step.

Also update the big comment above this effect (currently ending "...Doing the forward navigation from the onboarding screen instead raced this same `activeSemesters` live query...") — append one sentence so future readers know the exception exists:
```tsx
  // Navigate imperatively, in an effect, instead of rendering a declarative
  // <Redirect> tied to `pathname`/`activeSemesters` changing together. The
  // declarative form caused a real "Maximum update depth exceeded" crash
  // on-device the moment `/(tabs)` became a real route (previously it just
  // 404'd, masking the loop): navigating away from onboarding, re-rendering
  // this layout with a not-yet-updated `activeSemesters` (the live query's
  // change-driven refresh hadn't landed yet), rendering <Redirect> back to
  // onboarding, and repeating — all within React Navigation's synchronous
  // re-render cascade for a single navigation transition, hitting React's
  // nested-update ceiling. Running the redirect in a `useEffect` instead
  // lets each navigation settle (commit) before the next one is even
  // considered, breaking that cascade.
  // This effect owns BOTH directions of the redirect, not just "push into
  // onboarding when there's no semester". `app/onboarding/primer-semestre.tsx`
  // deliberately does NOT call router.replace("/(tabs)") itself after
  // creating a semester — it just awaits the write and lets this effect
  // react once the live query actually reflects it. Doing the forward
  // navigation from the onboarding screen instead raced this same
  // `activeSemesters` live query (its change-driven refresh from the INSERT
  // hadn't landed yet when the screen navigated), so the freshly-mounted
  // `/(tabs)` route would render with stale `hasActiveSemester = false`,
  // this effect would send it straight back to onboarding, and the user
  // would see the form reset to empty with no visible error — reproduced
  // on-device. Making this effect the single source of truth for both
  // directions means the forward navigation only ever fires once
  // `hasActiveSemester` has actually flipped true, never before.
  // Phase 10.5: `primer-semestre.tsx` now DOES navigate itself, but only to
  // `/onboarding/perfil` (never straight to `/(tabs)`) — `onProfileStep`
  // above stops this effect from yanking the user out of that screen the
  // instant `hasActiveSemester` flips true. `perfil.tsx` is the one screen
  // allowed to call `router.replace("/(tabs)")` directly, since by the time
  // it does, `hasActiveSemester` is already guaranteed true (the semester
  // write happened first, on the previous screen) — no race.
```

```tsx
import { useState } from "react";
import { Alert, StyleSheet, Text, TextInput, TouchableOpacity, View } from "react-native";
import { router } from "expo-router";

import { saveProfile } from "@/db/repositories/settings";
import { colors } from "@/theme";

export default function OnboardingPerfilScreen() {
  const [nickname, setNickname] = useState("");
  const [fullName, setFullName] = useState("");
  const [saving, setSaving] = useState(false);

  async function handleContinue() {
    setSaving(true);
    try {
      await saveProfile({
        nickname: nickname.trim() || null,
        fullName: fullName.trim() || null,
      });
      router.replace("/(tabs)");
    } catch {
      setSaving(false);
      Alert.alert("Error", "No se pudo guardar el perfil. Inténtalo de nuevo.");
    }
  }

  return (
    <View style={styles.container}>
      <Text style={styles.title}>¿Cómo te llamamos?</Text>
      <Text style={styles.body}>
        Puedes cambiar esto más tarde desde Configuración. Este paso es opcional.
      </Text>
      <TextInput
        style={styles.input}
        placeholder="Apodo (ej. Ale)"
        placeholderTextColor={colors.textMuted}
        value={nickname}
        onChangeText={setNickname}
        autoFocus
      />
      <TextInput
        style={styles.input}
        placeholder="Nombre completo (opcional)"
        placeholderTextColor={colors.textMuted}
        value={fullName}
        onChangeText={setFullName}
      />
      <TouchableOpacity style={styles.button} onPress={handleContinue} disabled={saving}>
        <Text style={styles.buttonText}>{saving ? "Guardando…" : "Continuar"}</Text>
      </TouchableOpacity>
    </View>
  );
}
```
